# Ресерч: техническая реализация загрузки файлов встречи

**Основание:** [plan-meeting-file-upload.md](./plan-meeting-file-upload.md), [prd-meeting-file-upload.md](./prd-meeting-file-upload.md)
**Дата:** 2026-11-18
**Статус:** Research (решения не приняты, требуется spike из раздела 6)

## 1. Вопросы

1. Как принимать multipart-файл до 500 МБ в NestJS 12 (Express) так, чтобы лимит 413 срабатывал до приёма тела и без буферизации файла в памяти.
2. Как писать файл на диск под сгенерированным именем и не оставлять мусор при отказе.
3. Как проверять формат по расширению, MIME и (желательно) сигнатуре содержимого.
4. Как браузер отправляет 500 МБ через приложение web и получает прогресс и отмену.
5. Как отдавать файл (стриминг, `Content-Disposition` с кириллицей) и удалять файлы вместе с встречей.

## 2. Находки, которые меняют план

### 2.1. Next.js rewrites обрезают тело запроса на 10 МБ (блокер)

Текущий `apps/web/next.config.ts` проксирует `/api/*` на API через `rewrites`. По результатам поиска ([обсуждение и PR](https://github.com/agegr/pi-web/pull/846), [issue #938](https://github.com/sydevs/SahajCloud/issues/938), [документация proxyClientMaxBodySize](https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize)):

- Next.js клонирует и буферизует тело проксируемого запроса в памяти, по умолчанию обрезая его на **10 МБ**, без ошибки для клиента.
- Для rewrites это тоже применимо (сообщалось в PR, на который я ссылаюсь выше).
- Сервер API получит усечённый multipart, и запрос упадёт с ошибкой разбора тела, которая плохо диагностируется.

Вывод: загрузку нельзя пускать через Next-прокси, пока не доказано обратное. Варианты:

| Вариант                                                                                       | Плюсы                                                        | Минусы                                                                  |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **A. Браузер шлёт файл напрямую в API** (`NEXT_PUBLIC_API_URL`, CORS в NestJS для origin web) | Нет буферизации Next, прогресс XHR честный, нет лишнего хопа | Нужна настройка CORS и env; токен в заголовке (уже так)                 |
| B. Поднять `proxyClientMaxBodySize` до 500+ МБ                                                | Остаётся same-origin                                         | Буферизация 500 МБ в памяти Node на каждый запрос; плохо масштабируется |
| C. Исключить маршрут загрузки из прокси (matcher / отдельный route)                           | Потоковая передача                                           | Сложнее конфигурация, зависит от версии Next                            |

**Рекомендация: вариант A.** Прокси оставить для остальных эндпоинтов (JSON), а загрузку и, при желании, скачивание отправлять на прямой адрес API. Это же снимает вопрос с буферизацией при скачивании (стриминг через прокси Next тоже не гарантирован).

Проверка до старта фазы 4 (spike, см. раздел 6): загрузить файл 100 МБ через текущий `rewrites` и через прямой запрос, сравнить размер, принятый сервером.

### 2.2. Multer уже есть в дереве зависимостей

В pnpm-хранилище присутствуют `multer@2.5.0` и `busboy@1.6.0` (транзитивно, через `@nestjs/platform-express`) и `file-type@22.3.0`. Следствия:

- Не нужно ставить сторонний парсер. Использовать `FileInterceptor` из `@nestjs/platform-express` (он поднимает multer).
- Версия multer зависит от версии `@nestjs/platform-express`. Закрепить её явно в `apps/api/package.json` при установке, чтобы не получить скрытое обновление. Версия multer, которую подтянет NestJS, не проверена по исходникам: в ходе поиска этого подтвердить не удалось.
- `file-type` тоже транзитивный. Если нужна проверка сигнатуры (раздел 3.3), добавить его как прямую зависимость.

### 2.3. Лимит 500 МБ: два уровня, и multer сам по `Content-Length` не отказывает

Multer сам по себе не проверяет `Content-Length`: в его `limits` по умолчанию `fileSize` равен `Infinity` (подтверждено по документации npm-пакета). Поэтому:

1. **До приёма тела** (раньше интерцептора) — guard или middleware читает `Content-Length`:
   - если больше `500 МБ + запас` на multipart-накладные расходы, отвечать **413** сразу. Запас (например, 1 МБ) нужен, потому что тело multipart больше самого файла на заголовки и границы;
   - если заголовка нет (chunked), полагаться на уровень 2.
2. **При потоковом приёме** — `limits.fileSize = 500 * 1024 * 1024` в multer. Превышение даёт ошибку `LIMIT_FILE_SIZE`, которую нужно маппить в 413 фильтром исключений.

Важно: порядок «guard → interceptor» в NestJS означает, что guard отработает до тела, а проверка количества файлов (409) должна стоять **до записи на диск**, иначе файл сначала сохранится, а потом будет удалён. Поэтому количество проверяем в guard/сервисе по БД до запуска multer, а при гонке параллельных запросов допускаем превышение на 1 и страхуемся транзакцией при вставке записи (или счётчиком `SELECT ... FOR UPDATE` по встрече).

### 2.4. MIME от клиента ненадёжен

`file.mimetype` в multer берётся из заголовка части multipart, который задаёт клиент. Поэтому:

- Белый список строим как пару «расширение → допустимые MIME» (как и предупреждает план).
- Для mp3, wav, m4a, ogg, mp4, webm, mov проверяем сигнатуру содержимого (`file-type` или собственная проверка первых байт: `ID3`/`FF Fx` для mp3, `RIFF....WAVE`, `OggS`, `ftyp` для mp4/m4a/mov, `EBML` для webm). Это ответ на «формат по расширению и MIME»: сигнатура страхует от подмены.
- Отказ по сигнатуре: 400, файл удаляется с диска.

## 3. Рекомендуемый стек и подход

### 3.1. Приём файла (API)

- `FileInterceptor('file', { storage: diskStorage({ destination: MEETING_FILES_DIR, filename: () => randomUUID() }), limits: { fileSize: MAX_BYTES, files: 1, fields: 0 } })`.
- Имя из запроса не используется на диске (требование PRD). `originalname` сохраняется только в БД. Для кириллицы имя приходит в UTF-8 в заголовке части, но multer может отдать его как latin1. Нужно декодировать (`Buffer.from(name, 'latin1').toString('utf8')`) и проверить на реальном файле в spike.
- При отказе (расширение, сигнатура, лимит) — удалить записанный файл. Multer при ошибке лимита удаляет частичный файл (проверить в spike), но явный `unlink` в catch нужен на всех остальных ветках.

### 3.2. Схема и метаданные

Соответствует плану: `MeetingFile` с `onDelete: Cascade`, поле `storedName` (UUID). Дополнительно предлагаю `@@index([meetingId])`.

### 3.3. Очистка при удалении встречи

`DELETE /meetings/:id` сначала читает `storedName` всех файлов встречи, затем удаляет запись (каскад в БД), затем удаляет файлы с диска через `fs.promises.rm(path, { force: true })`. `force` делает повторный запуск безопасным. Ошибки удаления с диска логировать, но не возвращать 500 клиенту: запись в БД уже удалена, и это осиротевший файл, который можно подчистить отдельной задачей. Для v1 достаточно логировать.

### 3.4. Скачивание

- `fs.createReadStream` в `StreamableFile` (NestJS), `Content-Length` из БД.
- `Content-Disposition: attachment; filename="<ascii-fallback>"; filename*=UTF-8''<encodeURIComponent(name)>` — стандартная схема для кириллицы. Использовать `encodeRFC5987`-подобную функцию или `encodeURIComponent` с заменой `'()*` на `%XX`.
- Совпадение SHA-256 проверяется в e2e тесте (план фаза 2).

### 3.5. Клиент (web)

- Загрузка: `XMLHttpRequest` с `upload.onprogress` (проценты) и `xhr.abort()` (отмена). `fetch` для загрузки не подходит: прогресса upload в нём нет. Именно XHR в плане выбран правильно.
- Адрес: прямой адрес API (вариант A из раздела 2.1), с `Authorization: Bearer`. Нужен CORS в NestJS (`enableCors({ origin: WEB_ORIGIN, allowedHeaders: ['Authorization'] })`), переменная окружения в `.env.example`.
- Скачивание: `fetch` с Bearer, затем `blob` и `URL.createObjectURL`. Имя из `Content-Disposition` (`filename*`). Для больших файлов blob держит всё в памяти браузера (до 500 МБ). Альтернатива — прямая ссылка с токеном в query, но это утечка токена в логах; её не рекомендую.
- Перетаскивание: HTML5 drag-and-drop, предварительная проверка расширения и размера в браузере.

### 3.6. Тесты

- API unit: функция валидации (пары расширение/MIME, сигнатура, граница 500 МБ, граница 5 файлов).
- API e2e: supertest с `attach()` для загрузки реальных маленьких фикстур (не 500 МБ: для границы хватает проверки `Content-Length` без отправки тела, а для стриминга можно временно понизить лимит через конфиг). Проверка, что после отказов каталог файлов пуст.
- Web: Vitest + Testing Library, замоканный `XMLHttpRequest` для прогресса и отмены (план фаза 4).

## 4. Что НЕ рекомендуется

- `express.raw` / чтение тела в память: 500 МБ в буфер на запрос.
- Загрузка через Server Actions Next.js: по умолчанию лимит 1 МБ, отдельная настройка и та же история буферизации.
- Presigned-загрузка в S3/MinIO: вне скоупа PRD (локальный диск).
- Имя файла из запроса в пути на диске: требование PRD и защита от path traversal.
- Токен в query string для скачивания.
- Библиотеки tus/resumable: resumable вне скоупа PRD.

## 5. Риски и открытые вопросы

| #   | Риск                                         | Митигация                                                 |
| --- | -------------------------------------------- | --------------------------------------------------------- |
| R1  | Next.js обрезает тело на 10 МБ               | Вариант A (прямой запрос к API) + spike                   |
| R2  | Гонка при проверке количества файлов (409)   | Транзакция/`FOR UPDATE` по встрече                        |
| R3  | Кодировка имени в multipart (latin1 vs utf8) | Декодирование + тест с «Запись встречи.mp3»               |
| R4  | Осиротевшие файлы при сбое удаления с диска  | Логирование; при необходимости задача очистки             |
| R5  | Версия multer меняется вместе с NestJS       | Явно закрепить транзитивную версию или прямую зависимость |
| R6  | Диск заполняется (до 2.5 ГБ на встречу)      | Вне скоупа; указать в README требования к диску           |
| R7  | CORS для прямого запроса с браузера          | Явный `origin` из env, без `*` при `Authorization`        |

Открытые вопросы для владельца продукта:

1. Подтвердить вариант A (прямой адрес API для загрузки и скачивания, CORS) вместо прокси Next. Это меняет план фазы 1 (CORS и env) и фазы 4.
2. Нужна ли проверка сигнатуры содержимого (`file-type`) или достаточно расширения и MIME, как в PRD? Рекомендую сигнатуру: это одна зависимость и защита от подмены.

## 6. Spike перед стартом (до фазы 1, около 1–2 часов)

1. Поднять текущий `rewrites` и загрузить файл 50 МБ через `/api/...`; сравнить размер, полученный NestJS (ожидается обрезка на 10 МБ).
2. Тот же файл напрямую на API с CORS: размер совпадает.
3. Проверить, что multer при `LIMIT_FILE_SIZE` удаляет частичный файл в `destination`.
4. Проверить имя файла с кириллицей и пробелами, пришедшее через multipart.
5. Проверить `Content-Length` до тела: отказ 413 без чтения тела (через guard).
